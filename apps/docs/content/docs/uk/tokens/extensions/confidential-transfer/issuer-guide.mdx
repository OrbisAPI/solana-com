# Випуск токенів Confidential Transfer на Solana

Цей посібник призначений для **емітентів**: команд, які створюють та
обслуговують мінт Token-2022 з розширенням Confidential Transfer. Він охоплює
рішення, які ви приймаєте під час створення мінту, та операції, які ви виконуєте
протягом усього його циклу. Для огляду дій з боку власника (депозит,
застосування, переказ, виведення) зверніться до покрокових сторінок, а для
підтримки цих токенів у продукті — до
[Посібника з інтеграції](/docs/tokens/extensions/confidential-transfer/integration-guide).

Конфіденційні перекази зберігають суми переказів та залишки на рахунках у
зашифрованому вигляді, лишаючи адреси рахунків, мінт і власників
загальнодоступними. Вони покладаються на ZK ElGamal Proof Program для
верифікації доказів у мережі, тому мінт можна використовувати на кластерах, де
ця програма увімкнена.

## Рішення, які ви приймаєте при створенні

Розширення Confidential Transfer необхідно ініціалізувати до ініціалізації
монетного двору і не можна додати пізніше. При створенні ви вирішуєте:

- **Політика підтвердження**: чи можуть акаунти самостійно підключатися до
  конфіденційних переказів без дозволу (`auto`) або мають бути підтверджені
  органом конфіденційних переказів монетного двору (`manual`).
- **Аудитор**: чи встановлювати глобальний ElGamal публічний ключ аудитора, щоб
  призначена сторона могла розшифровувати кожну суму переказу для монетного
  двору. Необов'язково і може бути змінено пізніше.
- **Необов'язкові супутні розширення**: конфіденційні комісії за переказ (у парі
  з розширенням комісії за переказ) і конфіденційний випуск/спалювання — обидва
  розглянуті нижче. Вони також мають бути ініціалізовані при створенні.

## Створення конфіденційного монетного двору

CLI встановлює політику підтвердження за допомогою
`--enable-confidential-transfers auto` або `manual`; `auto` дозволяє будь-якому
власнику налаштувати власний акаунт, тоді як `manual` обмежує це підтвердженням
від органу конфіденційних переказів (який за замовчуванням є органом монетного
двору). Клієнтські шляхи використовують ті самі налаштування через параметри
`ConfidentialTransferMint`: орган, прапорець автоматичного підтвердження та
необов'язковий ключ аудитора. Як політику підтвердження, так і аудитора можна
змінити пізніше (див. [Налаштування аудитора](#configure-an-auditor)); лише
наявність самого розширення фіксується при створенні.

<CodeTabs>

```terminal !! title="create-confidential-mint.sh"
$ spl-token --program-id TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb create-token --enable-confidential-transfers auto
```

```rust !! title="create-confidential-mint.rs"
use spl_token_client::token::ExtensionInitializationParams;

let extensions = vec![ExtensionInitializationParams::ConfidentialTransferMint {
    authority: Some(authority.pubkey().into()),
    auto_approve_new_accounts: true, // false for a manual approve policy
    auditor_elgamal_pubkey: None,    // Some(pubkey) to set a global auditor
}];

token
    .create_mint(&mint_authority, freeze_authority.as_ref(), extensions, &[&mint_keypair])
    .await?;
```

```ts !! title="create-confidential-mint.ts"
import { getCreateAccountInstruction } from "@solana-program/system";
import {
  extension,
  getMintSize,
  getInitializeConfidentialTransferMintInstruction,
  getInitializeMintInstruction,
  TOKEN_2022_PROGRAM_ADDRESS
} from "@solana-program/token-2022";

// Size the mint account to include the confidential transfer extension.
const space = BigInt(
  getMintSize([
    extension("ConfidentialTransferMint", {
      authority: authority.address,
      autoApproveNewAccounts: true, // false for a manual approve policy
      auditorElgamalPubkey: null // an ElGamal pubkey Address to set an auditor
    })
  ])
);
const rent = await rpc.getMinimumBalanceForRentExemption(space).send();

// Create the account, initialize the extension, then initialize the mint, in one
// transaction. The extension instruction must come before InitializeMint.
const instructions = [
  getCreateAccountInstruction({
    payer,
    newAccount: mint, // mint keypair signer
    lamports: rent,
    space,
    programAddress: TOKEN_2022_PROGRAM_ADDRESS
  }),
  getInitializeConfidentialTransferMintInstruction({
    mint: mint.address,
    authority: authority.address,
    autoApproveNewAccounts: true,
    auditorElgamalPubkey: null
  }),
  getInitializeMintInstruction({
    mint: mint.address,
    decimals,
    mintAuthority: mintAuthority.address,
    freezeAuthority: null
  })
];
// Sign with the payer and mint keypair, then send.
```

</CodeTabs>

## Налаштування аудитора

Глобальний аудитор — це ElGamal публічний ключ, що зберігається на монетному
дворі. Якщо він встановлений, кожен конфіденційний переказ додатково шифрує суму
за цим ключем, тому той, хто має відповідний секретний ключ, може розшифровувати
всі суми переказів для монетного двору. Саме так конфіденційні перекази
залишаються сумісними з вимогами аудиту та відповідності: публіка нічого не
бачить, аудитор бачить усе.

Уповноважений з конфіденційних переказів може встановити, змінити або видалити
аудитора в будь-який момент. Та сама операція також оновлює політику
підтвердження. У CLI ключ аудитора — це кодування base64 відкритого ключа
ElGamal; передайте `--auditor-pubkey none`, щоб видалити його, та
`--approve-policy auto|manual`, щоб змінити політику.

Ротація стосується лише майбутніх переказів. Суми в транзакціях, що вже є в
блокчейні, залишаються зашифрованими для того ключа аудитора, який був активним
під час їх виконання, тому зберігайте старі ключі аудитора, якщо вам потрібно
розшифрувати історичну активність.

<CodeTabs>

```terminal !! title="update-confidential-settings.sh"
$ spl-token update-confidential-transfer-settings <MINT_PUBKEY> --auditor-pubkey <AUDITOR_ELGAMAL_PUBKEY>
```

```rust !! title="update-confidential-settings.rs"
token
    .confidential_transfer_update_mint(
        &authority,
        true,                         // auto_approve_new_account
        Some(auditor_elgamal_pubkey), // None to clear the auditor
        &[&authority_keypair],
    )
    .await?;
```

```ts !! title="update-confidential-settings.ts"
import { getUpdateConfidentialTransferMintInstruction } from "@solana-program/token-2022";

const ix = getUpdateConfidentialTransferMintInstruction({
  mint,
  authority, // confidential transfer authority (signer)
  autoApproveNewAccounts: true,
  auditorElgamalPubkey // an ElGamal pubkey Address, or null to clear
});
```

</CodeTabs>

<Callout type="warn">
  Секретний ключ аудитора може розшифрувати суму кожного переказу для монетного
  двору. Зберігайте його з такою самою суворістю, як і ключ підписання, та
  плануйте його ротацію. Встановлення аудитора в значення `None` відключає
  видимість сум для всіх, окрім власників облікових записів.
</Callout>

## Підтвердження облікових записів (ручна політика)

За ручної політики підтвердження обліковий запис, налаштований для
конфіденційних переказів, не може здійснювати конфіденційні транзакції, поки
уповноважений з конфіденційних переказів не підтвердить його. Це надає емітентам
можливість контролювати доступ для учасників зі списку дозволених або тих, хто
пройшов KYC. CLI не надає команди підтвердження, тому підтвердження виконується
через клієнт.

<CodeTabs>

```rust !! title="approve-account.rs"
token
    .confidential_transfer_approve_account(
        &token_account,
        &authority,
        &[&authority_keypair],
    )
    .await?;
```

```ts !! title="approve-account.ts"
import { getApproveConfidentialTransferAccountInstruction } from "@solana-program/token-2022";

const ix = getApproveConfidentialTransferAccountInstruction({
  token, // the token account to approve
  mint,
  authority // confidential transfer authority (signer)
});
```

</CodeTabs>

## Комісії за конфіденційні перекази

Якщо ваш монетний двір стягує
[комісію за переказ](/docs/tokens/extensions/transfer-fees), а перекази є
конфіденційними, комісія також має утримуватись конфіденційно. Розширення
`ConfidentialTransferFeeConfig` відповідає за це та ініціалізується під час
створення монетного двору разом із розширеннями для комісії за переказ і
конфіденційних переказів.

Утримані комісії накопичуються в зашифрованому вигляді на рахунках одержувачів,
потім збираються на монетний двір і виводяться уповноваженим із виведення
утриманих коштів. Кожна сума комісії залишається зашифрованою протягом усього
процесу. Нічого з цього не доступно через CLI. Секретний ключ ElGamal
уповноваженого із виведення утриманих коштів може розшифровувати суми утриманих
комісій, що в поєднанні з публічними параметрами комісії може розкрити
інформацію про суми переказів — тому ставтеся до цього ключа як до
конфіденційного.

### Ініціалізація конфігурації комісії

Додайте це разом із `ConfidentialTransferMint` та конфігурацією комісії за
переказ у тому самому створенні монетного двору.

<CodeTabs>

```rust !! title="init-confidential-fee.rs"
use spl_token_client::token::ExtensionInitializationParams;

ExtensionInitializationParams::ConfidentialTransferFeeConfig {
    authority: Some(authority.pubkey().into()),
    withdraw_withheld_authority_elgamal_pubkey: withdraw_withheld_elgamal_pubkey,
};
```

```ts !! title="init-confidential-fee.ts"
import { getInitializeConfidentialTransferFeeInstruction } from "@solana-program/token-2022";

const ix = getInitializeConfidentialTransferFeeInstruction({
  mint,
  authority, // authority allowed to change the withdraw withheld ElGamal key
  withdrawWithheldAuthorityElGamalPubkey // ElGamal pubkey Address
});
```

</CodeTabs>

### Збір та виведення утриманих комісій

Збір переміщує зашифровані утримані комісії з рахунків до монетного двору;
виведення переміщує їх із монетного двору на обраний рахунок. Задіяні дві
уповноважені особи, кожна з яких може відрізнятися від уповноваженої особи
монетного двору:

- **Уповноважена особа з конфіденційних комісій за переказ** (`authority`,
  встановлена на `ConfidentialTransferFeeConfig`) вмикає або вимикає збір.
- **Уповноважена особа з виведення утриманих коштів** (з `TransferFeeConfig`
  розширення комісії за переказ) виводить зібрані комісії з монетного двору.

Виведення потребує доказу рівності та діапазону, наданих безпосередньо або
підтверджених в облікових записах стану контексту.

<CodeTabs>

```rust !! title="harvest-withdraw-fees.rs"
// Permissionless: move withheld fees from accounts into the mint.
token
    .confidential_transfer_harvest_withheld_tokens_to_mint(&[&source_account])
    .await?;

// Withdraw withheld fees from the mint (requires the withdraw withheld authority).
token
    .confidential_transfer_withdraw_withheld_tokens_from_mint(
        &destination_account,
        &withdraw_withheld_authority,
        None, // proof context state account, supplied inline if None
        None, // withheld tokens info, fetched if None
        &withdraw_withheld_elgamal_keypair,
        &destination_elgamal_pubkey,
        &new_decryptable_available_balance,
        &[&withdraw_withheld_authority_keypair],
    )
    .await?;
```

```ts !! title="harvest-withdraw-fees.ts"
import {
  getEnableHarvestToMintInstruction,
  getHarvestWithheldTokensToMintForConfidentialTransferFeeInstruction
} from "@solana-program/token-2022";

// Allow accounts to harvest their withheld fees to the mint, signed by the
// confidential transfer fee authority.
const enableIx = getEnableHarvestToMintInstruction({ mint, authority });

// Permissionless: move withheld fees from accounts into the mint.
const harvestIx =
  getHarvestWithheldTokensToMintForConfidentialTransferFeeInstruction({
    mint,
    sources: [sourceAccount]
  });
```

</CodeTabs>

У JS-клієнті виведення зібраних комісій із монетного двору
(`getWithdrawWithheldTokensFromMintForConfidentialTransferFeeInstruction`)
додатково потребує доказу рівності та діапазону, підтвердженого в облікових
записах стану контексту, тому воно використовує ту саму схему з обліковими
записами доказів, що й конфіденційний переказ.

## Конфіденційний випуск і спалення

Розширення `ConfidentialMintBurn` дозволяє уповноваженій особі монетного двору
випускати та спалювати пропозицію безпосередньо через конфіденційні баланси,
зберігаючи загальну пропозицію зашифрованою. Монетний двір із цим розширенням
вимикає публічний шлях депозиту та виведення, оскільки токени існують лише
конфіденційно. Дивіться
[документацію протоколу](https://www.solana-program.com/docs/confidential-balances)
для повної моделі.

<Callout type="info">
  Конфіденційний випуск/спалення найпростіше реалізувати через Rust
  `spl-token-client`, який генерує необхідні докази та упорядковує транзакції за
  вас. JS-клієнт `@solana-program/token-2022` постачає низькорівневі
  конструктори інструкцій (`getConfidentialMintInstruction`,
  `getConfidentialBurnInstruction` та інші), але не містить високорівневого
  помічника для побудови доказів, і CLI-команди відсутні, тому наведені нижче
  приклади — лише на Rust.
</Callout>

Ініціалізуйте розширення під час створення монетного двору, після чого
здійснюйте карбування, спалення та узгодження постачання з часом. Карбування
випускає зашифровану суму на конфіденційний баланс отримувача; спалення видаляє
зашифровану суму до відкладеного спалення, яке пізніше включається до
постачання. Обидві операції генерують докази, як і конфіденційний переказ.

<CodeTabs>

```rust !! title="confidential-mint-burn.rs"
use spl_token_client::token::ExtensionInitializationParams;

// 1. Initialize at creation (alongside ConfidentialTransferMint).
ExtensionInitializationParams::ConfidentialMintBurn {
    supply_elgamal_pubkey, // encrypts the confidential supply
    decryptable_supply,    // AES ciphertext of the initial supply (zero)
};

// 2. Mint an encrypted amount into a recipient's confidential balance.
token
    .confidential_transfer_mint(
        &mint_authority,
        &destination_account,
        None, // equality proof account
        None, // ciphertext validity proof account
        None, // range proof account
        mint_amount,
        &supply_elgamal_keypair,
        &destination_elgamal_pubkey,
        auditor_elgamal_pubkey, // Option
        &supply_aes_key,
        None, // supply account info, fetched if None
        &[&mint_authority_keypair],
    )
    .await?;

// 3. Burn an encrypted amount from a holder's confidential balance into the
//    mint's pending burn. Generates proofs like a confidential transfer.
token
    .confidential_transfer_burn(
        &owner,
        &source_account,
        None, // equality proof account
        None, // ciphertext validity proof account
        None, // range proof account
        burn_amount,
        &source_elgamal_keypair,
        &supply_elgamal_pubkey,
        auditor_elgamal_pubkey, // Option
        &source_aes_key,
        None, // burn account info, fetched if None
        &[&owner_keypair],
    )
    .await?;

// 4. Fold the accumulated pending burn into the confidential supply.
token
    .confidential_transfer_apply_pending_burn(&mint_authority, &[&mint_authority_keypair])
    .await?;
```

</CodeTabs>

Змініть ключ шифрування постачання за допомогою
`confidential_transfer_rotate_supply_elgamal_pubkey` (відкладене спалення має
спочатку дорівнювати нулю), а також оновіть читабельний шифротекст постачання за
допомогою `confidential_transfer_update_decrypt_supply`.

## Операційні та комплаєнс-міркування

- **Зберігання ключа аудитора.** Якщо ви призначили аудитора, секретний ключ
  аудитора є ключем дешифрування з високою цінністю. Зберігайте та змінюйте його
  ретельно, і вирішіть, хто у вашій організації (або який регулятор) його
  зберігає.
- **Підхід до відповідності вимогам.** Перевірка адрес та аналіз графів
  контрагентів продовжують працювати, оскільки адреси залишаються публічними.
  Моніторинг на основі сум залежить від ключа аудитора або вибіркового розкриття
  від власників рахунків. Визначте свій підхід до запуску.
- **Підключення власників.** Налаштування конфіденційного рахунку потребує
  підпису власника. Щоб безперешкодно налаштовувати рахунки для користувачів,
  попросіть їх одноразово зареєструвати ключ ElGamal та використовувати шлях
  реєстру, описаний у
  [Посібнику з інтеграції](/docs/tokens/extensions/confidential-transfer/integration-guide#creating-and-configuring-accounts).
- **Кількість транзакцій.** Конфіденційний переказ наразі охоплює кілька
  залежних транзакцій, оскільки докази перевищують поточний ліміт розміру
  транзакції. Формат транзакцій v1 (що з'явиться з Agave v4.2) підвищує цей
  ліміт і, як очікується, дозволить здійснювати одну транзакцію в мережі.
