トランザクションは、すべての必須署名者から有効な
[署名](/docs/core/transactions/transaction-structure#signatures)が付与されている場合にのみ実行されます。ローカル開発では通常、[`Keypair`](/developers/cookbook/wallets/create-keypair)として鍵を保持し、直接署名します。本番環境では、重要な問題が異なります：**秘密鍵はどこに保管され、誰がそれを使って署名を承認できるのか？**

<Callout type="warn">
  秘密鍵をクライアントサイドのコードに埋め込んだり、フロントエンドにバンドルしたり、ソース管理にコミットしたりしないでください。鍵を入手した者は、そのアカウントの資金を完全に制御できます。
</Callout>

## 署名アプローチ

| アプローチ                     | 鍵の保管場所                                                  | 署名者                                     | 最適なユースケース                                           |
| ------------------------------ | ------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------ |
| **ローカルkeypair**            | マシン上のファイルまたは環境変数                              | コードが直接実行                           | ローカル開発、テスト、CI                                     |
| **ブラウザウォレット**         | エンドユーザーのウォレット（Phantom、Solflareなど）           | エンドユーザーがトランザクションごとに署名 | ユーザーが自身のトランザクションに署名するフロントエンドdApp |
| **クラウドKMS / HSM**          | ハードウェアベースの鍵管理サービス（AWS KMS、GCP KMS、Vault） | バックエンドがサービスに署名をリクエスト   | バックエンドサービス、資金管理、規制対応環境                 |
| **マネージド / MPCウォレット** | プロバイダーのインフラ全体で分割または管理                    | プロバイダーがポリシーに従って共同署名     | 組み込みウォレット、承認ワークフロー、機関向けカストディ     |

ローカルkeypairは、アプリケーション内に秘密鍵の素材を直接保持する唯一のアプローチです。すべての本番環境向けアプローチでは、鍵を専用インフラに保管し、そのインフラに代わって署名を行わせます。

## バックエンド署名

サーバーが署名を行う必要がある場合（手数料の支払い、プログラムトランザクションの送信、またはトレジャリーの運用など）、生のkeypairではなく専用の鍵管理バックエンドを使用してください。Solana
Foundationは[Keychain](/docs/tools/keychain)をメンテナンスしています。これは統合署名ライブラリ（RustおよびTypeScript）であり、上記の表に挙げたすべてのバックエンド（Memory、HashiCorp
Vault、AWS KMS、GCP
KMS、Fireblocks、Privy、Turnkey、CDP、Crossmint、Dfns、Para、Openfort、Utila）に対して単一の`SolanaSigner`インターフェースを提供します。

インターフェースはすべてのバックエンドで同一であるため、開発時はインメモリ鍵を使用し、アプリケーションコードを書き直すことなく設定変更だけで本番バックエンドに切り替えることができます。Keychainは[`@solana/kit`](/docs/clients/official/javascript)および[Rust SDK](/docs/clients/official/rust)と互換性があります。
