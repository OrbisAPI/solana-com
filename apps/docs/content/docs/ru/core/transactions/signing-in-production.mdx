Транзакция выполняется только при наличии действительной
[подписи](/docs/core/transactions/transaction-structure#signatures) от каждого
обязательного подписанта. В ходе локальной разработки ключ обычно хранится в
виде [`Keypair`](/developers/cookbook/wallets/create-keypair) и используется для
подписания напрямую. В продакшене важен другой вопрос: **где хранится приватный
ключ и кто вправе авторизовать подпись с его помощью?**

<Callout type="warn">
  Никогда не встраивайте приватные ключи в клиентский код, не включайте их во
  фронтенд-сборку и не коммитьте в систему контроля версий. Любой, кто получит
  ключ, получит полный контроль над средствами этого аккаунта.
</Callout>

## Подходы к подписанию

| Подход                         | Где хранится ключ                                               | Кто подписывает                                         | Лучше всего подходит для                                                       |
| ------------------------------ | --------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **Локальный keypair**          | Файл или переменная окружения на машине                         | Ваш код, напрямую                                       | Локальная разработка, тесты, CI                                                |
| **Браузерный кошелёк**         | Кошелёк конечного пользователя (например, Phantom, Solflare)    | Конечный пользователь, для каждой транзакции            | Фронтенд-dApps, где пользователи подписывают собственные транзакции            |
| **Облачный KMS / HSM**         | Сервис ключей с аппаратной защитой (AWS KMS, GCP KMS, Vault)    | Ваш бэкенд запрашивает подпись у сервиса                | Бэкенд-сервисы, казначейские операции, регулируемые среды                      |
| **Управляемые / MPC-кошельки** | Распределены или переданы на хранение инфраструктуре провайдера | Провайдер совместно подписывает согласно вашей политике | Встроенные кошельки, рабочие процессы согласования, институциональное хранение |

Локальный keypair — единственный подход, при котором необработанный ключевой
материал находится непосредственно в вашем приложении. Все производственные
подходы хранят ключ в специализированной инфраструктуре и делегируют ей
подписание от вашего имени.

## Подписание на стороне бэкенда

Когда серверу необходимо подписывать транзакции — оплачивать комиссии,
отправлять программные транзакции или управлять казначейством — используйте
специализированный бэкенд для управления ключами вместо «сырого» keypair. Фонд
Solana поддерживает [Keychain](/docs/tools/keychain) — унифицированную
библиотеку подписания (Rust и TypeScript), которая предоставляет единый
интерфейс `SolanaSigner` для всех бэкендов из таблицы выше: Memory, HashiCorp
Vault, AWS KMS, GCP KMS, Fireblocks, Privy, Turnkey, CDP, Crossmint, Dfns, Para,
Openfort и Utila.

Поскольку интерфейс идентичен для всех бэкендов, вы можете вести локальную
разработку с ключом в памяти, а затем переключиться на производственный бэкенд
через конфигурацию — без переписывания кода приложения. Keychain совместим с
[`@solana/kit`](/docs/clients/official/javascript) и
[Rust SDK](/docs/clients/official/rust).
