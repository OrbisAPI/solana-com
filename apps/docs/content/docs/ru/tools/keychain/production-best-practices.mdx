Keychain абстрагирует бэкенд подписи, однако эксплуатация подписанта в
продакшене по-прежнему остаётся вашей ответственностью. Эти практики применимы
ко всем бэкендам; см. [Выбор бэкенда](/docs/tools/keychain/choosing-a-backend)
для подбора подходящего.

## Разделите горячие и холодные подписанты

Используйте операционный подписант с небольшим балансом («горячий») для частых
автоматизированных транзакций и отдельный высоконагруженный («холодный»)
подписант для перемещения средств казначейства. Обеспечьте холодный подписант
MPC-кастодией или облачным HSM и требуйте политики подтверждения перед
подписанием. Поскольку интерфейс идентичен, каждая роль может использовать
разный бэкенд без изменения точек вызова.

## Выполняйте ротацию ключей осознанно

В Solana ключ подписи _является_ адресом аккаунта, поэтому ротация ключа создаёт
новый адрес. Планируйте ротацию как миграцию: подготовьте новый ключ,
переназначьте соответствующие полномочия (или переместите средства) на новый
адрес, затем выведите из эксплуатации старый. Используйте отдельные ключи для
каждой среды, чтобы ключи devnet никогда не использовались повторно в mainnet.

## Предоставляйте доступ с минимальными привилегиями

Ограничьте учётные данные каждого бэкенда минимумом, необходимым для подписания.
Для AWS KMS это `kms:Sign` и `kms:DescribeKey` на конкретном ключе;
предпочитайте роли IAM статическим учётным данным. Применяйте тот же принцип к
политикам Vault и ключам API управляемых кошельков.

## Планируйте обеспечение доступности

Удалённые бэкенды зависят от сетевого сервиса. Вызывайте `isAvailable()` перед
использованием подписанта, применяйте повторные попытки с экспоненциальной
задержкой при временных сбоях и определите резервный путь на случай отказов.
Keychain применяет HTTPS для удалённых бэкендов и устанавливает тайм-аут запроса
по умолчанию.

## Защита секретов и транспорта

- Все удалённые бэкенды взаимодействуют через HTTPS; конечные точки без HTTPS
  отклоняются.
- Передавайте API-ключи, токены и учётные данные через менеджер секретов или
  переменные окружения — никогда не прописывайте их в коде и не сохраняйте в
  системе контроля версий.
- Keychain очищает ответы об ошибках, чтобы секреты не попадали в журналы;
  убедитесь, что ваши собственные журналы не содержат учётных данных и ключевого
  материала в открытом виде.

## Мониторинг и аудит подписания

Отслеживайте успешность подписания, задержку и количество сбоев, настройте
оповещения при аномальных всплесках — см. метрики в разделе
[Готовность к продакшену](/docs/payments/production-readiness#monitoring).
Включите аудит-журналы на стороне провайдера (KMS, Vault или кастодиан) и
сверяйте их с транзакциями, отправляемыми вашим приложением.
